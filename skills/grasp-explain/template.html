TL;DR

  • What: Failed upstream calls are retried up to 3 times with backoff, inside the HTTP client.
  • Why: Sync jobs were failing on brief upstream blips; see D1 and D2.
  • Risk: med retries add latency and could amplify an outage.

    Why this shape: Only server errors and timeouts retry; client errors never will (D1).

+  if (attempt >= MAX_ATTEMPTS) return false;

+  return err.status >= 500 && err.status !== 501;

Decisions and trade-offs

#DecisionChosenRejectedWhy
D1What counts as retryable5xx (except 501) and timeoutsAny error: would retry bad requests foreverOnly transient failures can succeed on a retry.
D2Where retries liveHTTP client wrapperJob runner: repeats side effects · per call site: duplicated policy"One place to tune; jobs aren't idempotent."

Risks and checks

  • Retry storms if upstream stays down. Covered: client.spec.ts caps attempts at 3. Not covered: jitter under load.
  • Slower failures: a dead upstream now takes ~1.4 s to fail instead of ~0.2 s. Not covered: job timeout budget.

Terms

Idempotent
Safe to repeat: doing it twice has the same effect as doing it once.
Backoff
Waiting longer between each retry so a struggling service can recover.
